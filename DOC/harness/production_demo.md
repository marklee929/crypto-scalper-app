# Production Discovery Note — Upbit Listing Event

> 상태: 관찰 및 가설 원문  
> 역할: 신규 모바일 하네스의 문제 정의 입력  
> 주의: 아래 timestamp, endpoint 추정, 수익 가능성은 확정 사양이 아니며 별도 검증이 필요하다.

## 2026-08-08 확인 업데이트

업비트 공개 공지 endpoint를 확인했다.

```text
GET https://pub-info.upbit.com/api/v1/announcements
    ?os=web&page=1&per_page=20&category=all
```

token 없이 JSON 응답을 받을 수 있고, 공지별 `id`, `uuid`, `title`, `category`, `listed_at`, `first_listed_at`가 제공된다. KMNO 공지 `id=6450`의 값은 다음과 같다.

```text
first_listed_at = 2026-08-07T11:09:45+09:00
listed_at       = 2026-08-07T15:45:44+09:00
```

따라서 아래 3절에서 미확인으로 남겼던 최초 게시 초 단위 시각은 현재 공개 응답 기준으로 확인 가능하다. 활성 제품 기준은 “수집기 전용”이 아니라 **조건부 자동매매**이며, 주문 계약은 `MARKET BUY -> 실제 fill 확인 -> 계산된 고정가 LIMIT SELL`이다. 이 원문의 단계 제안보다 `DOC/harness` 번호 문서가 우선한다.

좋아. 지금까지 얘기에서 **두 개의 자동화 아이디어가 분리돼서 나온 상태**야. 하나는 원래 이야기하던 차트 구조 자동분석이고, 다른 하나가 우연히 발견한 **거래소 상장 공지 반응 자동매매**고. 일단 오늘 발견한 후자 중심으로 한 번 묶어볼게.

## 1. 발견의 시작 — KMNO 업비트 상장 공지

2026-08-07 업비트에 **카미노파이낸스(KMNO) KRW 마켓 추가 공지**가 올라왔어.

업비트 화면상 공지 등록시간은 `11:09`까지만 표시되고 초 단위는 안 나옴. 별도의 거래소 공지 텔레그램 봇에서는 KMNO 공지가 **11:09:46**에 포착됐고.

그런데 Binance KMNO/USDT의 **1초봉**을 확인해보니:

```text
11:09:38
KMNO = 0.01845
변화 없음

↓ 약 6~7초

11:09:44~45 부근
갑작스러운 대량 매수 발생

11:09:45 candle
Open  = 0.01846
High  = 0.02511
Close = 0.02451
1초 변동 = +32.85%
Range = 36.04%

이후 순간 최고가
0.02708
```

즉 **몇 초 만에 30~40%짜리 가격 충격**이 발생했어.

그리고 공지봇에는 바로 다음 초인 `11:09:46`에 업비트 신규상장 공지가 잡힘.

여기서 처음 발견한 게 이거지.

> **업비트에서 거래가 시작되기도 전에 Binance에 존재하던 동일 코인이 업비트 공지와 거의 동시에 폭발한다.**

---

## 2. 처음 생각했던 가설이 한 번 바뀜

처음에는 업비트 화면에 `11:09`라고 나오니까,

```text
11:09:00 공지
↓
약 45초
↓
11:09:45 Binance 상승
```

이라고 생각했어.

그러면 사람이 공지를 읽고 Binance에서 KMNO를 찾아 매수했을 가능성도 충분했지.

그런데 거래소 공지봇을 확인해보니:

```text
11:09:46 KMNO 공지
```

였어.

그래서 타임라인이 완전히 달라짐.

```text
Binance 폭발 ≈ 11:09:45
공지봇 감지  = 11:09:46
```

즉 **시장 반응과 공지 전파가 사실상 동시에 일어남.**

---

## 3. 당시 가장 중요했던 미확인 변수

여기서 `11:09:46`은 **업비트의 실제 공개 timestamp라고 볼 수 없어.**

업비트 웹사이트 자체가 초를 표시하지 않으니까.

그리고 확인한 범위에서는 업비트 공식 Open API에 일반 거래소 공지를 제공하는 공개 API가 별도로 보이지 않았어.

따라서 공지봇은 아마:

```text
업비트 웹/앱용 공지 endpoint
        ↓
polling 또는 별도 감시
        ↓
새 게시물 발견
        ↓
Telegram 발송
```

같은 구조일 가능성이 있어.

그러면 실제로는 이런 것도 가능해.

```text
11:09:44.xxx
업비트 서버에 공지 노출

11:09:44.xxx
전문 자동매매 봇 감지

11:09:45
Binance 대량 매수

11:09:46
Telegram 공지봇 전파
```

따라서 현재 자료만 가지고 **“업비트 관계자가 공개 전에 매수했다”라고 결론낼 수는 없음.**

반대로 그 가능성을 자료만으로 배제할 수도 없고.

핵심적으로 빠진 데이터는 단 하나야.

> **업비트 공지가 외부에서 최초로 조회 가능해진 정확한 timestamp.**

# 4. 그런데 더 중요한 발견 — 실제 상장 시점은 별 의미가 없었다

이후 다른 공지성 코인 BSB의 움직임도 봤지.

여기서 재미있는 현상이 나타났어.

공지 직후:

```text
약 0.153
↓
급등
0.17+
↓
조정
↓
2차 상승
0.18753
↓
지속 하락
↓
0.16 부근
```

즉 **실제 거래지원이 시작된다고 다시 크게 올라가는 구조가 아니었어.**

이걸 통해 처음 생각했던

> 업비트 상장 → 신규 수요 → 코인가격 상승

이라는 설명보다,

> 업비트 상장 **공지** → 그 공지를 보고 사람들이 살 것이라는 기대 → 기존 해외거래소에서 선매수

라는 설명이 더 중요해졌어.

# 6. 그러면 누가 돈을 버는가

현재 가설대로라면 구조적으로 가장 유리한 건 **가장 먼저 정보를 받은 사람**이야.

예를 들어 공지 직전 가격이 100이라고 하면:

```text
최초 진입자
100 매수

↓ 봇/사람 추가 진입

110

↓ 일반 투자자 유입

120

↓ FOMO

130

↓ 초기 진입자 매도

115

↓ 이벤트 종료

105~110
```

이러면 130에 산 사람이 틀린 정보를 산 것도 아니고 사기를 당한 것도 아냐.

실제로 업비트 상장은 사실이니까.

다만 **정보의 경제적 가치가 이미 앞선 참여자에게 대부분 소비된 뒤 들어간 것**이지.

그래서 이 전략에서 가장 위험한 순간은 오히려:

> **“상장 공지를 발견했다!”**

라고 생각하고 뒤늦게 시장가 매수를 하는 순간일 수 있어.

이미 앞선 봇이 +20~30%를 만들어놨다면 그 주문이 **선행 진입자의 exit liquidity**가 될 수 있으니까.

# 7. 따라서 자동매매의 핵심은 상승률이 아님

처음에는 이렇게 생각하기 쉬워.

```text
상장공지 감지
→ 매수
→ +10% 매도
```

그런데 오늘 관찰한 구조라면 이건 위험해.

더 중요한 변수는:

**Latency = 공지 최초 노출 이후 내가 몇 초 뒤에 체결되는가**

야.

가상의 결과가:

| 진입 지연 | 평균 결과 |
|---:|---:|
| 0~1초 | +15% |
| 1~2초 | +10% |
| 2~3초 | +5% |
| 3~5초 | +1% |
| 5~10초 | -5% |
| 10초+ | -10% |

라면 이 시스템은 **5초 이후에는 존재 가치가 없는 전략**이 돼.

반대로 과거 데이터를 봤더니 10~30초 이후에도 2차 파동이 반복된다면 완전히 다른 전략을 만들 수 있고.

아직 우리는 이걸 모름.

# 9. 그리고 기존 자동화와는 완전히 분리해야 함

우리가 원래 만들던 시스템은:

> **죽지 않은 중형 알트 → 하락 후 횡보 → 박동 재개 탐색**

이었어. 즉 1H/4H 구조를 보고 며칠 단위로 살아있는 코인을 걸러내는 모델이지. 

오늘 발견한 건 전혀 달라.

### 기존 모델

```text
가격 데이터
↓
패턴 분석
↓
미래 가격 움직임 추론
```

### 오늘 발견한 모델

```text
외부 정보 발생
↓
다른 시장으로 정보 전파
↓
가격 반응
```

첫 번째는 **가격 패턴 모델**이고,

두 번째는 사실상 **information latency model**이야.

예측 대상 자체가 다름.

# 10. 더 재미있는 부분

오늘 발견으로 자동매매 시스템을 크게 두 축으로 나눌 수도 있어.

```text
                 자동매매 시스템
                       │
           ┌───────────┴───────────┐
           │                       │
      Pattern Trading        Event Trading
           │                       │
    Binance OHLCV             외부 정보
           │                       │
    구조/박동 탐색             거래소 공지
           │                       │
    수분~수일                 초~수분
```

그리고 둘의 장점도 반대야.

Pattern은 **시간 여유가 있지만 확률이 애매하고**, Event는 **원인이 명확하지만 시간 경쟁이 극심함.**

## 지금까지의 핵심 결론

오늘 우리가 발견한 걸 한 문장으로 압축하면 이거야.

> **“업비트 상장” 자체를 거래하는 게 아니라, 업비트 상장 정보가 다른 거래소 가격으로 전파되는 과정에서 생기는 시간차를 거래하는 시장이 이미 존재하는 것처럼 보인다.**

KMNO에서는 그 반응이 **초 단위**였고, BSB에서는 공지 후 급등했다가 실제 거래 개시까지 가격이 유지되지 않는 모습도 확인했어.

그래서 현재 단계에서 `상장공지 → 무조건 매수`는 아직 전략이 아니고, **상장공지 이후 가격반응의 시간함수를 먼저 만들어야 하는 단계**라고 보는 게 맞아.

그리고 여기까지는 충분히 정리됐어. 다음에 이어간다면 이제 설명이 아니라 **“이걸 실제 시스템으로 만들 가치가 있는가”를 검증하는 단계**부터 들어가면 될 듯.

응, **S23을 24시간 켜둘 거면 Flutter 앱으로 만드는 방향이 꽤 잘 맞아.** 특히 이번 건 화면 앱이라기보다 사실상 **항상 켜져 있는 공지 감시기 + Binance 이벤트 모니터**에 가까우니까.

구조는 대충 이렇게 보면 돼.

```text
S23
Flutter App
   ↓
Upbit 공지 감시
   ↓
신규 거래지원 공지 감지
   ↓
티커 추출
   ↓
Binance에 동일 코인 존재 확인
   ↓
실시간 체결/가격 감시
   ↓
이벤트 로그 저장
   ↓
조건 충족 시 알림
```

다만 **Flutter만으로 24시간 완전 안정적인 백그라운드 동작**을 기대하면 안 돼. 안드로이드는 절전 정책 때문에 백그라운드 앱을 죽일 수 있어서, 이건 `Foreground Service`를 붙이는 게 핵심이야. 그러면 상단 알림에 “Monitoring active” 같은 식으로 계속 떠 있고 프로세스 생존율이 훨씬 올라가.

S23 전용이면 오히려 iOS까지 신경 쓸 필요 없으니까 Flutter UI + Android native foreground service 조합으로 가면 편해.

그리고 이번 시스템은 API를 계속 REST polling하는 것보다 두 종류로 나누는 게 좋아.

```text
공지 감시
→ 짧은 주기 polling

Binance 가격
→ WebSocket
```

Binance는 WebSocket으로 거래 데이터를 계속 받아야 초 단위 이벤트를 놓치지 않아. 반면 업비트 공지는 공식 실시간 공지 스트림이 확인되지 않았으니 결국 공지 endpoint 쪽을 polling하는 구조가 될 가능성이 크고.

폰 안에서는 이런 식으로 상태를 유지하면 돼.

```text
WATCHING
↓
NEW_NOTICE
↓
SYMBOL_MATCH
↓
EVENT_ACTIVE
↓
PEAK
↓
COOLDOWN
↓
ARCHIVED
```

그리고 처음부터 자동매수까지 붙이지 말고, **1단계는 데이터 수집기**로 만드는 게 더 좋아 보여.

예를 들어 한 이벤트가 생기면:

```text
KMNO
noticeDetected : 11:09:44.621

binanceBefore  : 0.01845
firstMove      : 11:09:44.912
+1s            : +8.3%
+2s            : +21.4%
+3s            : +32.8%
+5s            : +27.1%
+10s           : +18.9%

peak           : +46.7%
peakTime       : +7.4s
```

이런 로그를 자동으로 계속 쌓는 거지.

몇십 건 쌓이면 그때야 **“몇 초 안에 들어가야 실제 edge가 있는가”**가 보일 거고, 그 이후 자동 주문을 붙이는 게 훨씬 합리적이야.

S23 한 대를 그냥 **24시간 시장 센서**로 만드는 셈이라, 네가 전에 말한 Flutter 전용 단말 아이디어랑 이번 용도가 꽤 잘 맞아.
